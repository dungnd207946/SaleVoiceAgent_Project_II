01

Ẩn dụ não bộ — vì sao gọi là "Hippo"

HippoRAG mô phỏng lý thuyết chỉ mục hồi hải mã (hippocampal indexing theory) của trí nhớ dài hạn ở người. Trí nhớ con người không lưu mọi thứ dày đặc — nó lưu một chỉ mục thưa các khái niệm và các liên kết giữa chúng, rồi khi cần thì "kích hoạt lan truyền" từ vài khái niệm gợi ý ra toàn mạng liên tưởng.

Thay vì "một cú embedding rồi lấy top-K chunk gần nhất" (RAG cổ điển — mỗi chunk là một hòn đảo), HippoRAG dựng một mạng lưới nối các thực thể/khái niệm và đoạn văn lại. Truy hồi = thả "xác suất" vào vài node gợi ý rồi để nó lan qua các cạnh, nên một câu hỏi có thể kéo về những đoạn văn liên quan gián tiếp mà embedding thuần bỏ sót.
02

Giai đoạn OFFLINE — dựng đồ thị (một lần, lúc build)

Toàn bộ chi phí "nặng" nằm ở đây, chạy lúc build/ingest — không đụng vào latency của cuộc gọi. Trong repo của bạn, đây chính là chỗ móc của sparse_reconcile.reconcile() / lúc dựng FlatStore.

1

Cắt đoạn (chunk)

15 file ABOUT_<Name>.md → 285 chunk. Mỗi chunk thành một passage node.

2

OpenIE bằng LLM

LLM trích bộ ba (chủ thể · quan hệ · đối tượng) từ mỗi chunk. VD: (Noble Crystal, ở, Tây Hồ).

3

Dựng KG mở

Mỗi thực thể → phrase node; quan hệ → cạnh. Passage nối với phrase của nó bằng cạnh "contains". Phát hiện đồng nghĩa gộp node.

4

Nhúng & lưu

Embed cả passage lẫn phrase (e5-large sẵn có). Lưu graph + vector. Thêm doc mới = cập nhật tăng dần, không rebuild.

Khác biệt của HippoRAG 2 so với v1
v1 chỉ có phrase node. v2 đưa passage node vào chung một đồ thị với phrase node (nối bằng cạnh "contains"). Nhờ đó xác suất PPR chảy được phrase → passage → phrase, hợp nhất được thế mạnh của tìm kiếm thưa (khái niệm) và dày (ngữ cảnh) ngay trong một lần chạy.
03

Giai đoạn ONLINE — truy hồi (mỗi câu hỏi)

Đây là phần chạy trong lúc gọi điện. HippoRAG 2 gốc gồm 4 bước dưới. Ở phần Realtime tôi sẽ chỉ cách bỏ bước LLM (3b) để giữ TTFA cho voice.

①

Chọn seed dày (passage)

Embed câu hỏi → chấm điểm tương đồng với các passage node. Passage giống nhất trở thành seed "dày".

②

Chọn seed thưa (triple)

Đồng thời chấm điểm câu hỏi với các bộ ba/phrase. Thực thể/quan hệ khớp trở thành seed "thưa".

③

Recognition memory (LLM — sẽ bỏ ở bản realtime)

Một LLM lọc các triple top để chỉ giữ seed thật sự liên quan → tăng precision. Đây là lời gọi LLM query-time duy nhất, và là thứ đắt latency nhất.

④

Personalized PageRank

Bơm xác suất vào các seed rồi chạy PPR trên KG tĩnh. Xác suất lan qua cạnh. Passage node điểm cao nhất = kết quả trả về. Mili-giây, không LLM.

05

Personalized PageRank — mổ xẻ từng bước

Chính xác: sau bước 1 & 2, tập seed gồm cả hai loại node — phrase (từ seed thưa) và passage (từ seed dày). Cả hai sống chung một đồ thị duy nhất (điểm mấu chốt của HippoRAG 2), nên PPR đối xử với chúng như nhau. Dưới đây là toàn bộ cơ chế.

a) Trực giác — người đi bộ ngẫu nhiên "có thiên vị"

PageRank tưởng tượng một người đi bộ nhảy lung tung trên đồ thị. Điểm của một node = tần suất người đó ghé thăm nếu đi mãi mãi. "Personalized" chỉ thay đổi đúng một chỗ: khi người đi bộ "teleport", thay vì nhảy tới node bất kỳ, họ luôn quay về các seed.

🌐

PageRank cổ điển

Đi theo cạnh; thỉnh thoảng teleport tới một node bất kỳ, đều nhau. Trả lời câu hỏi "node nào quan trọng nói chung" — như Google xếp hạng web.

🎯

Personalized (PPR)

Y hệt, nhưng teleport chỉ quay về các seed của câu hỏi. Khối xác suất bị "ghim" quanh vùng liên quan → trả lời "node nào quan trọng đối với các seed này".

b) Công thức — đọc bằng lời

r  =  (1 − d) · s   +   d · Aᵀ · r
      └─ quay về seed ─┘   └─ đi bộ tiếp một bước ─┘

Lặp lại phép tính này tới khi r gần như không đổi. Ý nghĩa từng ký hiệu:

rVector điểm của mọi node (tổng luôn = 1). Đây là thứ ta đang tính.
sReset vector — chỉ seed khác 0. Vd: Tây Hồ=0.5, Bể bơi=0.5, mọi node khác = 0. Đây chính là chỗ "personalized".
dDamping (ở đây 0.5): xác suất "đi bộ tiếp". 1−d là xác suất "teleport về seed". d cao → lan xa hơn, d thấp → bám sát seed.
AᵀMa trận kề chuẩn hoá theo bậc: từ một node, chia đều xác suất cho các hàng xóm.

c) Chạy tay trên đồ thị Noble thu nhỏ

5 node, 5 cạnh vô hướng. Hai seed là Tây Hồ + Bể bơi (từ câu hỏi "dự án nào ở Tây Hồ có bể bơi?"). Cấu trúc:

  Tây Hồ ───── Noble Crystal ───── P·Tổng quan
  (seed)        │        │
  Bể bơi ───────┘        └───────── P·Tiện ích
  (seed) ───────────────────────────────┘

  Cạnh: Tây Hồ–NobleCrystal · Bể bơi–NobleCrystal
        NobleCrystal–P·Tổng quan · NobleCrystal–P·Tiện ích · Bể bơi–P·Tiện ích

Đánh số node: 1=Tây Hồ, 2=Bể bơi, 3=Noble Crystal, 4=P·Tổng quan, 5=P·Tiện ích. Bậc mỗi node: deg = [1, 2, 4, 1, 2].

① Ma trận kề A  — đối xứng, ô = 1 nếu có cạnh

        1   2   3   4   5
   1 [  0   0   1   0   0  ]
   2 [  0   0   1   0   1  ]
   3 [  1   1   0   1   1  ]   ← Noble Crystal nối 4 node
   4 [  0   0   1   0   0  ]
   5 [  0   1   1   0   0  ]

② Ma trận chuyển tiếp M  — chuẩn hoá mỗi CỘT theo bậc (chính là Aᵀ trong công thức)

Từ node j đi sang hàng xóm i với xác suất 1/deg(j) → chia mỗi cột cho bậc của node cột đó. Mỗi cột cộng lại = 1.

     từ →   1     2      3     4     5
  tới 1 [  0     0    0.25    0     0   ]
      2 [  0     0    0.25    0    0.5  ]
      3 [ 1.0   0.5     0    1.0   0.5  ]
      4 [  0     0    0.25    0     0   ]
      5 [  0    0.5   0.25    0     0   ]
          ───   ───   ────   ───   ───
   cột Σ = 1     1      1      1     1     ✓

③ Thế vào công thức — vòng lặp 1

r₁ = (1−d)·s  +  d·M·r₀        với  d = 0.5,   s = r₀ = [0.5, 0.5, 0, 0, 0]ᵀ

bước 1 — nhân M·r₀  (chỉ cột 1 & 2 khác 0 vì r₀ chỉ có seed):
   hàng 3 = 1.0·0.5 + 0.5·0.5 = 0.75      ← xác suất dồn vào Noble Crystal
   hàng 5 =           0.5·0.5 = 0.25      ← và một phần sang P·Tiện ích
   ⇒ M·r₀ = [ 0, 0, 0.75, 0, 0.25 ]ᵀ

bước 2 — trộn với reset:
   r₁ = 0.5·[0.5, 0.5, 0,    0, 0   ]     (số hạng quay-về-seed)
      + 0.5·[0,   0,   0.75, 0, 0.25]     (số hạng đi-bộ-tiếp)
      = [ 0.25, 0.25, 0.375, 0, 0.125 ]ᵀ   (tổng = 1 ✓)

Các vòng sau lặp lại đúng phép này (thay r₀→r₁→r₂…). Bảng dưới là kết quả từng vòng — bấm ▶ Bước lặp tiếp theo để chạy. Để ý: seed không "giữ" hết xác suất — nó chảy ra rồi được số hạng reset kéo về, cân bằng dần tới khi hội tụ.

Đọc kết quả cuối
HippoRAG trả về passage, nên chỉ xếp hạng 2 node passage: P·Tiện ích (0.109) > P·Tổng quan (0.027) → trả passage tiện ích của Noble Crystal cho Luna (nó khẳng định đúng: "Noble Crystal ở Tây Hồ có bể bơi"). Node phrase Noble Crystal tuy điểm cao nhưng không phải văn bản để nhét vào prompt — nó chỉ cho biết câu trả lời nói về dự án nào. Đáng chú ý: P·Tiện ích thắng vì nó nối thẳng tới cả hai seed-region, dù embedding câu hỏi không trỏ trực tiếp vào nó — đó là "suy luận đa bước".
Vì sao PPR không phá TTFA
Thực tế lặp ~10–50 vòng (hoặc tới khi thay đổi < ε). Trên đồ thị BĐS nhỏ của bạn (vài nghìn node), igraph/scipy giải bằng đại số ma trận thưa trong <1ms. Ma trận Aᵀ được precompute một lần lúc bootstrap — mỗi query chỉ là vài phép nhân vector. Đó là lý do bước nặng duy nhất (dựng graph + OpenIE) nằm hoàn toàn ở offline.
06

Áp dụng vào bài toán BĐS của Noble

Corpus của bạn cực kỳ hợp để dựng đồ thị vì nó đã có cấu trúc quan hệ tự nhiên: dự án ↔ khu vực ↔ tiện ích ↔ loại căn ↔ khoảng giá ↔ chủ đầu tư. Đây là các loại node/cạnh nên trích:

🏙️

Dự án

Noble Crystal, Alumi, Noble Palace… — trùng với 15 mã trong catalog.py.

📍

Khu vực

Tây Hồ, Long Biên, Tây Thăng Long — chính các token "mơ hồ" bạn đang phải xử lý ở find_project.

🏊

Tiện ích

bể bơi, gym, công viên, trường học — quan hệ (dự án)-[có]->(tiện ích).

🛏️

Loại căn

2PN, 3PN, penthouse, shophouse.

💰

Khoảng giá

Node giá rời rạc hoá (~3 tỷ, ~5 tỷ, >10 tỷ) để câu hỏi ngân sách bắt được.

🏗️

Chủ đầu tư

Nối các dự án cùng chủ đầu tư — trả lời "còn dự án nào của CĐT này?".

Điểm cộng riêng cho bạn
Cùng một đồ thị này tăng cường cả find_project: khi khách nói một cái tên nghe mơ hồ, PPR từ các gợi ý (khu vực + tiện ích khách vừa nhắc) có thể giúp phân định dự án — bổ trợ cho ProjectNameIndex hiện tại thay vì chỉ dựa trên phonetic.
07

Biến thể REALTIME + chỗ ghép vào code

HippoRAG 2 gốc có 1 lời gọi LLM query-time (recognition memory, bước ③). Với voice, ta bỏ nó khỏi hot path — đây là toàn bộ bí quyết giữ TTFA:

✗ Bản gốc (chậm cho voice)

Query → embed → chọn seed → LLM lọc triple (~0.5–2s) → PPR → trả về. Lời gọi LLM này cộng thẳng vào latency mỗi lượt.

✓ Bản realtime (đề xuất)

Query → embed (đã có) → hybrid RRF (đã có) → lấy top-K làm seed → PPR trên KG tĩnh (~5–30ms, không LLM) → fuse điểm vào RRF → trả về.

Nơi nó sống trong agent/rag/

Không thay thế gì cả — thêm một tầng mở rộng đồ thị mỏng ngay sau bước hybrid, trong query_noble_kb (file noble_kb.py bạn đang dùng):

# agent/rag/graph_expand.py  (module mới — thuần Python, không LLM)
import igraph, numpy as np

class GraphExpander:
    # Nạp 1 lần lúc bootstrap (giống ProjectNameIndex). Graph nhỏ → nằm gọn RAM.
    def expand(self, seed_chunk_ids, seed_weights, top_k=5):
        reset = np.zeros(self.n_nodes)
        for cid, w in zip(seed_chunk_ids, seed_weights):
            reset[self.node_index[cid]] = w        # bơm xác suất vào seed
        pr = self.g.personalized_pagerank(       # ← PPR, vài ms
                reset=reset.tolist(), damping=0.5)
        return self.rank_passages(pr, top_k)  # điểm PPR theo passage node

# noble_kb.py — trong _query_via_qdrant / _query_via_flat_store
hits = await query_hybrid(query, project_filter, top_k=20)   # như hiện tại
if settings.noble_graph_expand:                              # env bật/tắt như các backend khác
    seeds   = [(h.chunk_id, h.rrf_score) for h in hits[:8]]
    graph_hits = expander.expand(*zip(*seeds), top_k=5)      # +~10ms
    hits = fuse_rrf(hits, graph_hits)                          # gộp điểm, dedupe theo content_hash
return _format_hits(hits[:5])
Bám đúng hạ tầng bạn có
Dùng lại content_hash làm định danh chunk (đã có trong payload Qdrant), _format_hits của flat_store_adapter để giữ nguyên shape output, và dựng graph trong cùng reconcile() đã đọc root collection. Bật bằng env NOBLE_GRAPH_EXPAND — hỏng thì fallback về hybrid thuần, đúng pattern degrade sẵn có.

Lời khuyên trung thực trước khi bạn xây
Với corpus chỉ ~285 chunk và phần lớn câu hỏi là single-hop ("dự án X có bể bơi không?"), lợi ích của graph thường khiêm tốn — benchmark cho thấy single-hop factual thì RAG thường vẫn ngang hoặc hơn GraphRAG. Nên: (1) chạy make eval-estate để xác định lỗi thật là recall, ranking hay chunking; (2) cân nhắc một cross-encoder reranker nhẹ (~10ms) trước — ROI thường cao hơn và rẻ hơn graph. Graph tỏa sáng nhất ở câu đa bước / liên tưởng ("dự án nào cùng chủ đầu tư với X mà rẻ hơn?").
