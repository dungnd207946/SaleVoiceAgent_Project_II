Ngược lại: [`../../CLAUDE.md`](../../CLAUDE.md)

### One shared agent for N tenants (NOT a worker-pool-per-tenant)

**The deployment model is ONE shared agent process serving many tenants — not one worker/bundle per tenant.** Every request resolves its tenant per-request (`tenant/current.py::current_tenant()`, a `ContextVar`); all module-level caches are tenant-keyed so tenant A's data never bleeds into tenant B's turn (see the `tenant/` layout row). Voice: one LiveKit worker pool registers a SHARED `settings.livekit_agent_name` and serves all tenants — tenant travels in participant metadata. Chat: tenant travels in the `X-Tenant-Id` header.

**The only thing that differs between tenants is structured config — identity, scope, and which optional tools are on.** The prompt skeleton (persona SOUL/RULES, tool schemas, conversation flow) is IDENTICAL for every tenant. Two ways to source that config, gated by `AGENT_CONFIG_SOURCE`:

- **`legacy` (default)** — per-tenant bundle: `tenants/<id>/manifest.toml` + `persona/` dir (incl. `config.json`), from the in-wheel package or the MinIO tenant store. Current behavior, unchanged.
- **`db`** — **shared on-disk persona skeleton** (`src/noble_agent/persona/`) composed at runner-build time with **per-tenant config read from a Portal-owned Postgres VIEW** (`agent_published_config`). Skeleton SOUL/RULES carry `<!-- TOOL:x:START/END -->` region markers + `{{identity.*}}`/`{{scope.*}}` placeholders; disabled-tool regions are stripped, placeholders rendered, tool schemas built from the enabled set. No `config.json` on this path. This is the **SaaS direction** — a new tenant is a DB config row + a `publish`, no code deploy and no per-tenant bundle. See `docs/handoff/spec.md` (Portal↔Agent contract) and `docs/superpowers/plans/2026-08-04-agent-config-from-db-compose.md`.

**`db`-mode retires MinIO from the whole control-plane, not just persona/config (2026-08-04):** every serving-path surface that used to read the MinIO tenant store now reads Postgres instead — worker version resolution (`agent/facade.py::_resolve_current_version` reads `agent_published_config.version` directly, async — no MinIO pointer file), tenant context (`tenant/db_context.py::context_from_config` builds `TenantContext` from the published config, cached per-tenant; `tenant/loader.py::get_tenant_context()` returns it in db-mode instead of parsing `manifest.toml`), and the heartbeat (`tenant/pg_heartbeat.py` — `PgHeartbeatWriter` upserts `control.agent_heartbeats`, **beat-per-connection** since the agent role can't enumerate all provisioned tenants the way the MinIO store's `list_ids()` could; `deployment_id` is looked up per-tenant via `agent_api.deployments` keyed by process `kind`). **Two transport shapes for who drives the beat: chat** (aiortc, single-process) runs a `PgHeartbeatSupervisor` over `ActiveTenantTracker` (fed by `mark_active` in `NobleAgent.create`, same process) via `server/http.py`; **voice** (LiveKit, fork-per-job) can't share a module-global tracker across the fork, so it runs a fork-safe **per-job** `run_job_heartbeat` INSIDE `transport/livekit/worker.py::entrypoint` (`_start_job_heartbeat`) — beats that call's tenant for its lifetime, stopped when the session ends; `_start_heartbeat` (main process) starts NO thread in db-mode and stays the legacy-MinIO-only supervisor. Both transports still pick PG-vs-MinIO through `tenant/heartbeat.py::build_heartbeat_supervisor`. `storage/postgres_client.py::tenant_conn` now sets BOTH `app.current_tenant` (agent's own data-plane RLS) and `app.tenant_id` (Portal's control-plane RLS) per transaction. **MinIO (`tenant/store.py` + `noble-tenant` CLI) is retained ONLY for the `legacy` path** — `tenant/loader.py::_build_store` is explicitly marked legacy-only/deprecated; deleting it outright is a follow-up, not done. Contract Portal must ship: `docs/handoff/agent-postgres-read-contract.md` (`agent_api.tenant_status`/`tenant_keys`/`deployments` views + `agent_published_config` + write grant on `control.agent_heartbeats`).

**Gateway auth (2026-08-10): single domain, runtime-credentials API — orthogonal to `AGENT_CONFIG_SOURCE`.** The gateway no longer resolves tenant from a Host subdomain or reads `agent_api.tenant_status`/`tenant_keys` itself (`gateway/pg_registry.py` + the older `gateway/registry.py`/`errors.py` are deleted); every provider connects through ONE shared domain. `gateway/auth.py::authorize` takes the connection's Bearer API key and calls `gateway/credentials.py::CredentialsClient.authorize`, which POSTs it to `GATEWAY_CREDENTIALS_API_URL` (Portal-owned) and gets back `RuntimeCredentials` (tenant_id, PG role/password, storage/kb config, `expires_at`) — cached in-RAM per API key up to `min(expires_at, now+GATEWAY_CRED_CACHE_TTL_SEC)`, so a cache hit still serves while the credentials API is briefly down. Failures classify as `bad_credential` (wrong/revoked key → close 4001) vs `auth_api_unavailable` (API down/misconfigured/bad response → close 4001, distinct reason), so on-call doesn't chase a key rotation when the outage is infra. `gateway/chat_proxy.py` forwards the resolved PG role/password/expiry to the worker as `X-PG-Role`/`X-PG-Password`/`X-PG-Expires` (plus optional `X-PG-Deployment`/`X-PG-Kind`, added 2026-08-10 to feed the heartbeat's credential-first `deployment_id` lookup below); the worker registers them (`storage/tenant_credentials.py`) and PG call sites route through `storage/postgres_client.py::pool_for_tenant(tenant_id)` (per-tenant role pool built from `POSTGRES_SERVER_DSN`, falling back to the shared `POSTGRES_DSN` pool when no credential was forwarded — dev/REPL, or any stash/fetch failure). Config lost `gateway_base_domain`; gained `gateway_credentials_api_url` + `postgres_server_dsn`.

**Voice gets the same per-tenant credential via a Redis stash, not a direct header hop (2026-08-10).** Voice has no gateway→worker hop to carry a header — dispatch goes through LiveKit Cloud, and secrets can't ride in participant metadata — so the gateway writes the credential to Redis instead: `gateway/server.py::_stash_voice_credentials` calls `storage/credential_stash.py::stash`, which Fernet-encrypts `{role, password, deployment_id, kind, expires_at}` (key derived `SHA-256→urlsafe-b64` from `GATEWAY_WORKER_SECRET` — the same secret chat already required, no new env var) and `SET`s it at `noble:pgcred:<tenant>` with `TTL = expires_at` (Redis expires the key itself, no cleanup needed) right before dispatching the call. The LiveKit job ingests it at call start: `transport/livekit/worker.py::entrypoint` calls `credential_stash.fetch_and_register`, which decrypts and calls `tenant_credentials.register` — same registry chat uses — so `pool_for_tenant` builds the tenant-role pool for voice too. Every failure mode (empty secret, missing Redis key, decrypt/JSON error, malformed `expires_at`) degrades to `None`/`False` rather than raising; the call proceeds on the shared DSN, exactly like the no-credential case above. The heartbeat writer (`tenant/pg_heartbeat.py::PgHeartbeatWriter.beat`) also reads `deployment_id` straight off the registered credential when its `kind` matches, instead of `SELECT`ing `control.deployments` — the tenant-scoped app role has no grant on that control-plane table — falling back to the legacy DB lookup when no credential (or a mismatched `kind`) is present.

**`agent_key_id` — đóng dấu API key lên conversations (2026-08-19).** Response của runtime-credentials API có thêm trường optional `agent_key_id` (định danh API key phía Portal, KHÔNG phải secret; Portal cũ chưa trả thì rỗng và mọi thứ chạy như cũ). Gateway parse nó vào `RuntimeCredentials.agent_key_id` rồi lan truyền per-CONNECTION — không nhét vào registry `tenant_credentials` làm nguồn đọc cho chat vì registry đó keyed theo tenant, mà một tenant có nhiều key (chat/voice) sống đồng thời sẽ ghi đè nhau. Chat: `chat_proxy.proxy_headers` forward header `X-Agent-Key-Id` (độc lập với bộ `X-PG-*` — key không kèm PG role vẫn đóng dấu được); worker `ws_handler::_agent_key_from_headers` chỉ tin header khi `GATEWAY_WORKER_SECRET` được cấu hình (cùng gate chống poison với `X-PG-*`) rồi set contextvar `tenant/current.py::current_agent_key_id` ngay trong task per-connection. Voice: field đi thêm trong payload Fernet của `credential_stash` (đường Redis `noble:pgcred:<tenant>` — ở đây per-tenant là chấp nhận được vì mỗi dispatch stash ngay trước đó); `fetch_and_register` đăng ký vào `TenantPgCredential.agent_key_id`, rồi `credential_stash.adopt_agent_key` set contextvar cho job. Điểm ghi duy nhất: `pg_data_plane._agent_key_id()` đọc contextvar trong `seed_conversation`/`persist_conversation` → cột `tenant_data.conversations.agent_key_id` (**BIGINT** — Portal đã tạo cột trước theo id số của `control.agent_keys`; contextvar giữ string nên convert sang int TẠI biên ghi này, giá trị không phải số → NULL + warning. Bài học 2026-08-19: để lọt string xuống asyncpg với cột bigint là `DataError` giết cả INSERT → mất luôn row conversations, mà seed/persist nuốt lỗi im lặng). NULL khi không qua gateway — dev/REPL/telephony; merge-upsert `COALESCE` nên seed mỗi lượt không xoá giá trị cũ. Contextvar chảy qua `fire_and_forget` vì `asyncio.create_task` copy context — không phải sửa chữ ký orchestrator/facade.

**5 core tools always union** (`update_customer` / `kb_search` / `find_project` / `escalate` / `no_lookup_needed` — `escalate` is the safety valve, never disable-able), **9 optional tools** provider-tick. That is the complete set of 14 built-ins — there are no "reserved" tools any more (the 3 post-sale ones were deleted 2026-08-18). `feng_shui` only takes effect when `recommend_units` is enabled. Canonical lists live in `agent/agent_config.py` (`CORE_TOOLS` / `OPTIONAL_TOOLS`).

**Two more PG roles for the optional `analyze_projects` tool (2026-08-26), sitting alongside the app-role/tenant-role roles described above:** `agent_kb_view_owner` (`NOLOGIN NOBYPASSRLS`) owns the 2 read-only views the tool queries (`agent_projects_v` / `agent_units_v`) — NOBYPASSRLS so the base-table RLS the views select from still applies when queried through the owner. `agent_sql_ro` (`NOLOGIN`) has `GRANT SELECT` on only those 2 views — nothing else. Both are provisioned once via `noble-tenant pg-ensure-sql-ro` (`tenant/pg_provisioning.py::ensure_sql_ro_roles`). Membership in `agent_sql_ro` is granted to the **shared app role** (`POSTGRES_APP_ROLE`) AND to **every per-tenant LOGIN role**, not just one or the other — the gateway's per-tenant-credential path (chat header / voice Redis stash, see above) connects PG **as the tenant role**, not the app role, so `SET LOCAL ROLE agent_sql_ro` inside `analytics.py::run_readonly` would fail on that path without the per-tenant grant too. `provision()` (new-tenant role creation) grants it automatically going forward.
