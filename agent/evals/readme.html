Noble Evals Runbook

Hướng dẫn setup và chạy toàn bộ bài đánh giá: chất lượng agent theo turn/multi-turn, retrieval + generation, latency từng component, và khả năng chịu tải — case/golden tạo & duyệt bằng labeller, kết quả ghi vào registry theo dõi được qua git.

Tổng quan — 4 suite, 1 registry

Mọi thứ nằm trong package evals/ (không đụng src/), gọi qua một CLI duy nhất python -m evals hoặc các target make eval-*. Mỗi run append một dòng tổng hợp vào evals/registry.jsonl (tracked trong git); chi tiết per-case nằm ở evals/reports/<run_id>/ (gitignored).

quality

Full-pipeline agent, per-turn & multi-turn. Deterministic: policy, tool selection, trajectory, run integrity, latency. Thêm --judge: 3 rubric LLM — correctness / groundedness / multiturn.

rag

Retrieval tách khỏi agent: recall@k, context recall/precision, MRR, empty-rate trên golden set v2 (nhiều chunk + answer, duyệt bằng labeller). Thêm --judge: stage generation cô lập (faithfulness, correctness, refusal).

bench

Latency từng component: STT, TTS, speaker, VAD, LLM — p50/p95/p99 + error rate.

load

CCU ramp tìm knee: chat WS (kèm assert admission 4029/503), voice LiveKit, từng service.

Entrypoint: _cmd_rag — đo retrieval tách khỏi agent trên golden set v2 đã duyệt: recall@k, context recall/precision@k (precision là lower bound — mẫu số là k, golden không phủ hết chunk liên quan), MRR, empty_rate, latency p50/p95. Cần Qdrant + embed; không cần Redis; LLM chỉ khi --judge.

Tham sốDefaultÝ nghĩa
--goldenbắt buộcFile golden JSONL schema v2 (golden_chunks: [{chunk_id, evidence}] + answer) — mọi dòng phải status: "approved" (duyệt bằng labeller), còn dòng draft là runner từ chối cả file. File rỗng → exit 1, không ghi registry.
--tenantnobleSet contextvar tenant → quyết định collection Qdrant <tenant>_documents.
--top-k5Số kết quả lấy về mỗi query; cũng là trần của recall@k (k ≤ top-k).
--modestructuredstructured = gọi thẳng Qdrant hybrid, chấm theo chunk id (đo retrieval thuần). agent-string = đi qua query_noble_kb như agent gọi thật, chấm theo evidence trong chuỗi trả về (đo cái agent thấy).
--judgefalseThêm stage generation cô lập (không qua agent): generator prompt cố định trả lời từ chunks đã retrieve → judge chấm faithfulness_rate, rag_answer_correctness_mean (so answer golden), rag_refusal_rate. Model generator: env EVAL_RAG_GEN_MODEL (fallback JUDGE_MODEL).
--judge-budget-usdNoneTrần chi phí judge của stage generation.

scripts/eval_with_key.sh wrapper của evals run

Dành cho tenant db-mode: config nằm sau RLS, chỉ PG role per-tenant đọc được. Script POST API key lên GATEWAY_CREDENTIALS_API_URL (đúng việc gateway làm) → nhận tenant_id + role/password PG → dựng POSTGRES_DSN per-tenant chỉ trong process này → exec python -m evals run --tenant <tenant> …. Credential hết hạn ~1h, fetch mới mỗi lần chạy.

Fetch một lần, không gia hạn. Lượt dài hơn TTL (~1h — bộ 100 case tuần tự đã ≈40–60 phút) có thể hỏng giữa đường khi pool cần mở connection mới bằng password đã hết hạn. Lượt dài thì dùng EVAL_TENANT_API_KEY (cách A): harness gọi lại mỗi case và tự lấy credential mới đúng lúc hết hạn. Key ở đây nằm trong argv nên hiện ra trong ps và history của shell — cách A truyền qua env nên kín hơn.
Tham sốDefaultÝ nghĩa

Tạo & duyệt case — Labeller

Case quality và golden RAG đều là JSONL schema v2, sống trong repo. Đường tạo/duyệt chính là labeller — không sửa tay bằng editor nữa (labeller validate bằng đúng loader nên không lưu được file hỏng):

make eval-labeller   # http://127.0.0.1:8765

Scorer kích hoạt theo NỘI DUNG block, không theo tag — khi viết case, chọn block theo thứ muốn đo:

Muốn đoĐiền blockScorer / metric
Chính sách trả lờiexpect (reply_contains / reply_not_matches / escalated / customer_field…)policy → policy_violations
Chọn tool + tham sốgolden.tools (matcher contains/equals cho từng arg), golden.banned_toolstool_selection → tool_selection_accuracy, arg_accuracy, banned_call_rate
Chất lượng câu trả lờigolden.answer (đáp án chuẩn — đúng ý là đạt)judge (--judge) → correctness + groundedness
Giữ ngữ cảnh nhiều lượtcase ≥2 turnsjudge multiturn → context_retention_score, consistency_score

tags (policy·tool·qa·multiturn·smoke) chỉ để lọc bằng --tag. Ba key tool_called/tool_not_called/tool_arg của schema cũ bị loader từ chối trong expect — chúng đã chuyển sang golden.tools/banned_tools. Case phải bật reviewed (phím a) mới được chấm. File mẫu đủ 7 pattern: evals/quality/data/cases/du_test/p1_examples.jsonl.

Chạy Quality — đánh giá agent per-turn / multi-turn

Credential per-tenant — làm trước, không thì cả bộ case chết

Harness drive agent in-process, mà gateway là chỗ duy nhất trong production đổi API key → PG role/password per-tenant rồi đăng ký vào storage.tenant_credentials. Không có entry đó, pool_for_tenant rơi về shared POSTGRES_DSN; với tenant db-mode thì RLS trả 0 row chứ không lỗi → mọi case chết bằng RuntimeError: no published config for tenant '…'. Hai đường làm việc của gateway, chọn một:

CáchDùng khi
A. EVAL_TENANT_API_KEY — harness tự lấy credential (evals/tenant_creds.py), gọi lại mỗi case nên tự gia hạn khi hết TTLMặc định. Chạy được với mọi make eval-*, và là cách duy nhất an toàn cho lượt dài hơn 1 giờ (bộ 100 case chạy tuần tự ≈ 40–60 phút, sát trần TTL)
B. scripts/eval_with_key.sh — wrapper dựng POSTGRES_DSN per-tenant rồi exec python -m evals runChạy nhanh một bộ nhỏ; tiện vì tự suy --tenant từ chính key. Fetch một lần, không gia hạn giữa lượt
# A — đường mặc định (key đi qua env, không nằm trong argv nên không lộ ra `ps`):
export EVAL_TENANT_API_KEY=ody_ag_<API_KEY_CỦA_TENANT>
make eval-quality ARGS="--tenant du_test --case POL-001,TOOL-001,QA-001"

# B — wrapper, tự suy tenant từ key:
scripts/eval_with_key.sh ody_ag_<API_KEY_CỦA_TENANT> --case POL-001,TOOL-001,QA-001

Kết quả mong đợi: từng case ok, 6 gate ✓, verdict PASS, một dòng mới trong registry.

Không đặt biến mà tenant vẫn cần credential? Harness in đúng một dòng hướng dẫn rồi dừng sớm ở case đầu tiên gặp no published config — thay vì để bạn đọc 100 dòng ERROR giống nhau. Tenant chạy shared DSN (noble) thì không cần đặt gì, ensure() tự no-op.
Auth API có rate-limit (429). Gọi authorize liên tục sẽ ăn auth_api_unavailable. Cách A chỉ gọi khi credential hết hạn nên an toàn; nếu bạn tự viết script grounding thì phải cache credential ra file ngoài repo (chmod 600), đừng fetch mỗi process.

Chạy full bộ case + LLM judge

# toàn bộ case của tenant (deterministic, rẻ):
make eval-quality ARGS="--tenant aina_prod"
# kèm 3 rubric judge — correctness / groundedness / multiturn (có cache + trần chi phí):
make eval-quality ARGS="--tenant aina_prod --judge --judge-budget-usd 2"
# hoặc qua wrapper (cách B), tenant suy từ key:
scripts/eval_with_key.sh ody_ag_… --judge --judge-budget-usd 2
Case chưa duyệt không được chấm. Mọi scorer bỏ qua case reviewed: false — chúng vẫn chạy và vẫn ghi trace, nhưng không dịch chuyển bất kỳ số nào. Duyệt thiếu một nhóm là gate của nhóm đó hiện missing và FAIL (fail-closed). Ví dụ đã gặp: duyệt 95/100 case nhưng bỏ sót 5 case policy → gate policy_violations = missing.

Chấm lại không tốn tiền

RUN (đắt — gọi LLM) và SCORE (rẻ — đọc trace) tách đôi. Đổi ngưỡng/scorer xong chỉ cần:

make eval-score RUN=<run_id> ARGS="--tenant du_test"
# thêm judge cho run đã có sẵn trace:
python -m evals score --run-dir evals/reports/<run_id> --tenant du_test --judge
Đừng chạy lẻ một case. Mỗi gate cần đúng loại case làm mẫu — chạy thiếu loại thì gate không có mẫu và fail-closed (cố ý: thiếu bằng chứng không bao giờ được đọc thành đạt). Bộ smoke tối thiểu 3 case (du_test): POL-001 có expect (gate policy) + TOOL-001 có golden.tools với arg matcher và banned_tools (gate arg_accuracy + banned_call_rate) + QA-001. Tự soạn bộ khác thì phải giữ đủ các loại block đó, đặc biệt ≥1 case khai banned_tools — thiếu là gate banned_call_rate hiện missing và FAIL.

Chạy RAG — đo retrieval tách khỏi agent

1

Sinh golden set nháp từ corpus (read-only)

python -m evals gen-golden --tenant du_test --limit 50
2

Duyệt bằng labeller — bước bắt buộc

make eval-labeller → mode RAG golden, mở file du_test/draft-*.jsonl: xoá/sửa câu hỏi kém, xác nhận evidence là câu trích nguyên văn từ chunk, sửa answer cho chuẩn, rồi bấm a từng case (draft → approved), Ctrl+S lưu. Runner từ chối file còn dòng draft. Case cần nhiều chunk vàng: thêm chunk bằng nút trong editor.

3

Chạy và đọc số

python -m evals rag --golden evals/rag/data/golden/du_test/draft-<ts>.jsonl --tenant du_test
# kèm stage generation nếu muốn đo cả vế sinh câu trả lời:
python -m evals rag --golden <file> --tenant du_test --judge

Ra recall_at_1/3/5, context_recall/precision@k (precision là lower bound), mrr, latency p50/p95 và empty_rate; thêm --judge có faithfulness_rate / rag_answer_correctness_mean / rag_refusal_rate. Nếu >50% case trả rỗng, harness cảnh báo "backend degrade im lặng?" — kiểm tunnel Qdrant / EMBED_BACKEND trước khi đổ lỗi cho dữ liệu.

Chạy Bench — latency từng component

make eval-bench                                    # tất cả: stt, tts, speaker, vad, llm
python -m evals bench --components vad,llm --runs 20   # chọn lẻ, tăng số lần đo

Mỗi component: 1 lần warm-up (bỏ) + N lần đo → p50/p95/p99 và error rate. Service chưa chạy hoặc thiếu env (SPEAKER_REMOTE_URL…) thì bị skip, không chặn phần còn lại. VAD chạy in-process bằng đúng model Silero mà worker dùng; LLM đo TTFT qua đúng provider chain đang pin.

Chạy Load / CCU — khả năng chịu tải

Chỉ chạy trên staging/dev. LiveKit Cloud dùng chung giữa các môi trường — worker load test có thể "giật" cuộc gọi của server đang phục vụ khách thật.
# Chat: ramp 1,2,4,8,… tìm knee; --admission-cap kiểm close 4029 + /health/ready 503:
make eval-load ARGS="--max 64 --hold 60 --host ws://localhost:8766 --admission-cap 200"

# Voice qua LiveKit (--max 1 = đo full-pipeline voice đơn lẻ):
python -m evals load --target voice --max 32 --hold 60

# Ramp riêng từng service — trả lời "component nào nghẽn trước":
python -m evals load --target service --component tts --max 16

Knee = bậc concurrency cao nhất mà throughput còn scale ≥15% và lỗi <1% — chính là CCU bền vững tối đa của hệ.
